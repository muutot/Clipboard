# OCR 架构

## 产品目标

复制或截取图片后，应用在后台识别图片中的文字。用户搜索识别出的任意关键词时，应直接找到对应图片。

OCR 全程默认在本地执行，不上传图片或识别结果。

## 处理管线

```text
剪贴板图片
  → 计算内容哈希并去重
  → 保存原图与缩略图
  → SQLite 写入图片记录（立即显示）
  → 后台 OCR 任务队列
  → 保存识别文字、文字块和模型版本
  → 更新 Tantivy 搜索索引
  → 搜索命中文字时返回原图片
```

剪贴板监听、缩略图生成、OCR 和搜索索引更新必须运行在独立任务中，不能阻塞界面线程。

## OCR 引擎选择

采用可替换的 `OcrEngine` 接口，业务层不直接依赖某个模型。

首选实现方向：

- PaddleOCR 中文检测与识别模型
- ONNX Runtime 跨平台推理
- Windows、macOS、Linux 共用相同模型和预处理逻辑
- 根据设备能力控制线程数和执行提供程序

不优先使用系统 OCR API，因为各平台能力、语言支持和结果结构差异较大。Tesseract 可以作为兼容或开发阶段的备用引擎，但不作为中文体验的最终标准。

## 数据模型

OCR 结果与图片记录保持一对一关系，建议包含：

```text
item_id
status                 pending / processing / completed / failed
engine
model_version
language
full_text
blocks_json            文字、置信度和图片坐标
image_hash
created_at
completed_at
error_message
```

搜索索引只保存搜索所需文字和记录 ID；完整文字块与坐标保存在 SQLite 中。

## 去重与重建

- 使用图片内容哈希复用已有 OCR 结果
- 模型版本变化时只重新处理旧版本结果
- OCR 失败需要保留状态并支持有限次数重试
- 搜索索引损坏时，从 SQLite 的 OCR 结果重建
- 删除图片记录时，同时清理 OCR 数据、索引文档和资源文件

## 界面状态

图片项目应能显示以下状态：

- 等待识别
- 正在识别
- 已识别，可查看或复制文字
- 识别失败，可重试

搜索结果可以突出显示命中的 OCR 文字片段；后续可根据文字块坐标在图片预览中高亮对应区域。

## 初始性能目标

- 图片写入历史列表不等待 OCR 完成
- 相同图片不重复识别
- OCR 并发默认限制为一个任务，避免抢占前台资源
- 搜索索引在 OCR 完成后快速增量刷新
- 超大图片先缩放或分块，限制峰值内存占用
