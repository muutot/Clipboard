# OCR 架构

## 产品目标

复制或截取图片后，应用在后台识别图片中的文字。用户搜索识别出的任意关键词时，应直接找到对应图片。

OCR 全程默认在本地执行，不上传图片或识别结果。

## 处理管线

```text
剪贴板图片
  → 计算内容哈希并去重
  → 保存原图与缩略图
  → SQLite 写入图片记录（立即显示）
  → 后台 OCR 任务队列
  → 保存识别文字、文字块和模型版本
  → 更新 Tantivy 搜索索引
  → 搜索命中文字时返回原图片
```

剪贴板监听、缩略图生成、OCR 和搜索索引更新必须运行在独立任务中，不能阻塞界面线程。

## OCR 引擎选择

采用可替换的 `OcrEngine` 接口，业务层不直接依赖某个模型。

首选实现方向：

- PaddleOCR 中文检测与识别模型
- ONNX Runtime 跨平台推理
- Windows、macOS、Linux 共用相同模型和预处理逻辑
- 根据设备能力控制线程数和执行提供程序

不优先使用系统 OCR API，因为各平台能力、语言支持和结果结构差异较大。Tesseract 可以作为兼容或开发阶段的备用引擎，但不作为中文体验的最终标准。

模型下载（`install_ppocr`）受隐私开关约束：开启"仅本地模式"时拒绝联网下载；下载使用带超时的 HTTP 客户端，完整性按文件字节数加本地 TOFU 摘要校验——下载成功后计算 SHA-256 并写入 `<文件名>.sha256`，再次安装时若磁盘文件与记录摘要不符则重新下载。不依赖上游固定哈希，模型更新无需维护 pin 值。

## 数据模型

OCR 结果与图片记录保持一对一关系，建议包含：

```text
item_id
status                 pending / processing / completed / failed
engine
model_version
language
full_text
blocks_json            文字、置信度和图片坐标（ppocr 引擎；tesseract 仅输出纯文本，无几何数据，故为空数组）
image_hash
created_at
completed_at
error_message
```

搜索索引只保存搜索所需文字和记录 ID；完整文字块与坐标保存在 SQLite 中。

## 去重与重建

- 使用图片内容哈希复用已有 OCR 结果
- 模型版本变化时只重新处理旧版本结果
- OCR 失败需要保留状态并支持有限次数重试
- 搜索索引损坏时，从 SQLite 的 OCR 结果重建
- 删除图片记录时，同时清理 OCR 数据、索引文档和资源文件

重试的实际形态（`ocr/worker.rs`）：

- **自动**：单张图片最多 `MAX_RECOGNITION_ATTEMPTS`（3）次识别尝试，首次失败后按 1s → 2s → 4s 退避。
  重试队列只存在 worker 内存里，数据库行在整段重试窗口内保持 `processing`，因此界面显示「正在识别」是诚实的；
  进程崩溃时的中断由启动时 `requeue_interrupted_ocr` 把 `processing` 复位为 `pending` 覆盖。
  之所以不把失败行重新入队：`claim_next_ocr` 按 `created_at_ms` 排序，重新入队会让同一行在下一个轮询周期立刻被再次领取，
  其他待识别图片被迫等完整段退避。
- **手动**：详情面板「重新识别」调用 `regenerate_clipboard_item_ocr`，次数不受限，并同时作废同哈希的其他记录以便重算。
- 预算耗尽后才把最后一次的错误信息落为 `failed`，因此失败原因始终是最后一次尝试的真实原因。

## 界面状态

图片项目应能显示以下状态：

- 等待识别
- 正在识别
- 已识别，可查看或复制文字
- 识别失败，可重试

搜索结果可以突出显示命中的 OCR 文字片段；后续可根据文字块坐标在图片预览中高亮对应区域。文字块坐标已按上一节说明
映射回原图像素空间，因此该高亮功能可以直接使用，无需再做尺度换算。

## 初始性能目标

- 图片写入历史列表不等待 OCR 完成
- 相同图片不重复识别
- OCR 并发默认限制为一个任务，避免抢占前台资源
- 搜索索引在 OCR 完成后快速增量刷新
- 超大图片先缩放或分块，限制峰值内存占用

### 超大图片的实际处理（`ocr/ppocr.rs`）

只做了**缩放**，没有分块：

- 解码走项目自己的 `content::hash::decode_image_file`（与缩略图同一条路径），因此同样受
  `MAX_DECODE_DIMENSION = 16384` 与 `image` crate 默认 512 MiB 分配预算约束。
  此前用的是 oar-ocr 的 `load_image`，它只猜格式、不设上限。
- 解码后按最长边 `MAX_OCR_SIDE = 4000` 降采样再送入 `predict`。这个上限不是自定的 tunable，
  而是 oar-ocr 自己的 `DEFAULT_MAX_SIDE_LIMIT`：检测阶段本来就会把长边压到 4000 以内再缩到 960，
  所以 4000 以外的像素属于「解码了、分配了、然后丢掉」。16384×12288 的截图按 RGB 约 604 MB，缩到 4000 边约 34 MB。
- 检测返回的文字块坐标是在**送入图像**的坐标系里的，因此每一圈都会乘 `coordinate_scale` 映射回原图像素空间。
  否则限幅会悄悄把已存的所有文字框重定义到一张更小的画布上——而按坐标高亮（见上文「界面状态」）尚未实现，
  这个陷阱只会在以后实现高亮时才暴露。
