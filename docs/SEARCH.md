# 搜索架构

## 目标

剪贴板搜索需要在大量历史记录中保持低延迟，并正确处理中文、文件名、URL 和混合语言内容。

第一阶段的“模糊搜索”定义为：

- 查询可以包含一个或多个关键词
- 多个关键词采用 AND 语义，记录必须包含全部关键词
- 关键词顺序不影响结果
- 关键词不需要在原文中连续出现
- 连续、同序、距离更近的匹配获得更高分

例如存在以下记录：

```text
脸皮挺好
脸皮挺脏
```

查询 `脸 脏` 或 `脏 脸` 时，只返回 `脸皮挺脏`。

拼写纠错、编辑距离、拼音搜索属于后续增强能力，不与第一阶段的无序多关键词匹配混为一谈。

## 技术选择

采用两层数据架构：

- SQLite 是唯一真实数据源，保存剪贴板记录、元数据和资源路径
- Tantivy 是可丢弃、可重建的搜索索引，负责高性能全文检索

不把 SQLite FTS5 作为主搜索引擎，原因是默认分词器对中文单字及任意子串匹配支持有限。Tantivy 可以在 Rust 进程内运行，不需要额外搜索服务，也适合跨平台桌面应用。

## 索引策略

计划为每条记录建立以下搜索字段：

- `content_raw`：规范化后的完整文本
- `content_ngram`：中文及混合文本的 1～3 字符 N-gram
- `title`：文件名、链接标题或文本首行
- `source_app`：来源应用名称
- `ocr_text`：图片 OCR 得到的完整文字
- `kind`：文本、链接、图片或文件
- `created_at`：创建时间戳
- `is_favorite`：收藏状态

图片二进制和文件内容不进入索引。OCR 文字作为核心搜索字段写入，与普通文本使用相同的规范化和 N-gram 策略。命中 `ocr_text` 时，搜索结果返回对应的图片记录，而不是创建一条独立文本记录。

## 查询流程

1. 对查询执行 Unicode NFKC 规范化、大小写折叠和空白清理。
2. 将显式空格分隔的关键词去重。
3. 为中文和混合文本生成查询 N-gram。
4. 每个关键词生成一个 MUST 子句，实现无序 AND 匹配。
5. 使用连续短语、同序匹配和关键词距离计算额外得分。
6. 最后结合收藏状态、最近使用时间和创建时间进行轻量排序。

概念示例：

```text
输入：脏 脸
规范化关键词：[脏, 脸]
查询：MUST(脏) AND MUST(脸)
```

## 一致性与恢复

- 新记录先写入 SQLite，再异步写入 Tantivy
- 图片记录写入后立即可见，OCR 完成后再增量更新同一条搜索文档
- 删除和更新操作同时写入索引任务队列
- 索引保存格式带有独立版本号
- 应用异常退出后，可以从 SQLite 增量修复或完整重建索引
- 搜索索引不得成为用户数据的唯一副本

## 初始性能目标

- 10 万条文本记录下，普通查询 P95 小于 30 ms
- 输入到界面更新的整体延迟目标小于 50 ms
- 查询工作不阻塞剪贴板监听和界面线程
- 连续输入通过短防抖和查询取消避免无效工作
