# 搜索优化对比测试报告

- 日期：2026-08-04
- 环境：Windows 11 Pro，Intel Core i7-13700KF，63.8 GB RAM
- 工具链：rustc 1.97.1 / cargo 1.97.1，`--release` 模式
- 基线代码：`086f0f6`（未提交任何优化改动）
- 基准测试文件：`src-tauri/tests/search_bench.rs`（`#[ignore]`，不进常规测试套件）

---

## 1. 背景与目标

参照 Everything 的索引方案，对剪贴板项目（SQLite 唯一数据源 + Tantivy 全文索引）提出 4 项候选优化：

| 编号 | 优化                                                  | 对标 Everything   |
| ---- | ----------------------------------------------------- | ----------------- |
| #1   | Tantivy `order_by_fast_field` 直接按 FAST 字段排序    | 1.4 版"Fast sort" |
| #2   | 把 outbox 同步移出搜索热路径（后台 worker）           | 实时后台更新索引  |
| #3   | 分词压缩：title 用 ngram(1,3) + content 用 ngram(2,3) | 索引体积/内存控制 |
| #4   | fast-field 排序后直接按序取 id，跳过 Rust 内存排序    | 免二次排序        |

测试目的：用真实管线测量各项优化的收益与代价，再决定是否提交。

---

## 2. 测试方法

### 2.1 语料

确定性伪随机生成（种子 42），贴近真实剪贴板历史：20 个中文词 + 10 个中文尾缀 + 10 个英文词，拼接成"标题 + 长文本"。规模取 2 万 / 8 万条。

### 2.2 索引变体

- **A（基线，当前线上方案）**：单 `content` 字段，ngram(1,3)，`created_at_ms` 为 FAST 字段 —— 与 `src/search/schema.rs` 一致。
- **B（#3 方案）**：`title` 字段 ngram(1,3) + `content` 字段 ngram(2,3)；查询时 1 字符词路由到 title，≥2 字符词路由到 content（对齐 `SearchQuery::required_ngrams` 语义）。

### 2.3 查询类别

`single_char_cn`（单字"脏"）、`bigram_cn`、`two_terms_cn`、`en_term`、`mixed_long`，各 40 次取 P50/P95。

### 2.4 #2 同步开销测量

用真实 `Database` + `SearchSynchronizer::sync_until_idle`，在 outbox 待处理 0/100/1000/10000 条时测量排空耗时（这正是当前搜索命令在待处理事件时阻塞支付的代价）。

### 2.5 管线对比（#1/#4）

对同一查询，比较两条路径：

- 基线：相关度 TopDocs → 逐个读 `created_at_ms` → Rust 降序排序（模拟现有 `apply_sort_rules`）。
- fast：`TopDocs::with_limit(500).order_by_fast_field::<i64>("created_at_ms", Desc)` 直接得有序 id。

---

## 3. 测试结果

### 3.1 索引体积与构建时间

| 规模   | 基线 A 构建 | 方案 B 构建 | A 体积  | B 体积  | 体积差     |
| ------ | ----------- | ----------- | ------- | ------- | ---------- |
| 20,000 | 320 ms      | 304 ms      | 2.07 MB | 1.78 MB | **-14%**   |
| 80,000 | 966 ms      | 624 ms      | 8.29 MB | 7.33 MB | **-11.5%** |

方案 B 构建快约 **27%~35%**，体积小约 **12%~14%**（content 少存 1 字 grams）。

### 3.2 搜索延迟 P50/P95（毫秒）

| 查询       | 规模 | 基线 A P50/P95 | 方案 B P50/P95      |
| ---------- | ---- | -------------- | ------------------- |
| 单字 中文  | 80k  | 0.071 / 0.098  | **0.0022 / 0.0059** |
| 双字 中文  | 80k  | 0.043 / 0.048  | 0.047 / 0.060       |
| 双词 中文  | 80k  | 0.045 / 0.065  | 0.046 / 0.063       |
| 英文词     | 80k  | 0.005 / 0.010  | 0.005 / 0.005       |
| 混合长查询 | 80k  | 0.011 / 0.013  | 0.012 / 0.012       |

- **单字查询：B 快约 32 倍**（0.07ms → 0.002ms），因 1 字 grams 只在很小的 title 字段存在。
- 其余查询类别两者基本持平（毫秒级内噪声）。

### 3.3 #1/#4 fast-field 排序 vs 相关度+内存排序（毫秒）

| 规模 | 相关度+Rust 排序 P50/P95 | fast-field P50/P95 |
| ---- | ------------------------ | ------------------ |
| 20k  | 0.0047 / 0.0052          | 0.0055 / 0.0086    |
| 80k  | 0.0116 / 0.0132          | **0.0215 / 0.339** |

**fast-field 排序反而更慢（约 2 倍），且 P95 出现 0.34ms 抖动。** 原因是 `order_by_fast_field` 需要对每个匹配文档计算排序键并维护 top-k 堆；而 BM25 相关度 top-k 在扫描 postings 时内联计算、开销更小。

### 3.4 #2 outbox 同步耗时（搜索热路径阻塞代价）

| 待处理事件数  | sync_until_idle P50/P95 |
| ------------- | ----------------------- |
| 0（空闲探测） | 0.0065 ms               |
| 100           | **4.14 ms**             |
| 1,000         | **18.3 ms**             |
| 10,000        | **227 ms**              |

空闲时探测仅 6.5μs（已有 `has_pending_outbox_events` 廉价探测，正常无阻塞）。一旦积压（批量导入 / 批量恢复 / 长时间未同步），首次搜索会被阻塞数十~数百毫秒。

---

## 4. 逐项分析与建议

### #1 / #4：fast-field 排序 —— **不建议采用**

- 实测在 2 万 / 8 万规模下都比现有"相关度 + Rust 排序"慢约 **2 倍**，P95 抖动明显。
- 副作用：排序键改为创建时间后，会丢失当前的相关度兜底排序（`search-cache-strategy.md` 明确保留该回退顺序）。
- 关键认知：Everything 的"Fast sort"针对的是**线性 strstr 扫描**引擎；Tantivy 的 BM25 得分本身就是高效的 top-k，不存在 Everything 那种"排序慢"的问题。
- **结论：当前数据规模（远低于 30ms 目标）下是纯回归，不提交。**

### #2：后台同步 outbox —— **有条件建议**

- 积压 1k 事件 = 18ms、10k = 227ms 的阻塞真实存在，且完全可被后台 worker 吸收。
- 现状已有廉价空闲探测兜底，只有"积压首次搜索"才付代价。
- **建议**：若确认存在批量导入/恢复等突发写入场景，加一个后台排空 worker（复用 `sync_until_idle`），让搜索前的待处理窗口趋近于 0。改动面：`lib.rs` 生命周期 + worker 启停，属中等风险。

### #3：分词压缩 —— **收益明确但牺牲单字内容召回，需产品决策**

- 收益：索引体积 **-12~14%**、构建 **-27~35%**、单字查询快 32 倍。
- 代价：单字查询（如"脏"）**只能命中标题，不再命中正文**。这与 `docs/SEARCH.md` 定义的"单字 CJK 需匹配任意位置"**冲突**，是召回率回归。剪贴板历史里单字查正文（"账""密""图"）是常见用法。
- **结论**：直接落地会破坏文档契约。若接受"单字只搜标题"的产品取舍可落地；否则需设计混合方案（如 content 保留 1 字 gram 的字段单独存放）。

---

## 5. 总体结论

1. **Tantivy 搜索本身已极快**：8 万条数据所有查询 P95 < 0.1ms，远低于 30ms 目标。四项优化里有三项（#1/#3/#4）都在优化一个已经空闲的路径。
2. **唯一真实的热路径成本是 #2**（待处理事件阻塞），但其仅在积压时出现。
3. **当前判定：四项均不建议在本轮提交**。
   - #1/#4 是确定性回归（实测更慢）；
   - #3 牺牲单字正文召回，违反既有契约，需先做产品取舍；
   - #2 收益真实但属架构改动，应在确认有突发写入场景后再做，并单独提交。
4. 基准测试框架 `src-tauri/tests/search_bench.rs` 已保留（`#[ignore]`），可随时重跑对比验证。

### 后续可留档的候选

- 真实管线中 `get_items_by_ids`（≤500 条 SQLite 读取）是查询尾部的另一成本点，未列入本次 4 项，建议后续单独测。
- 若未来结果集超 `searchPageSizeLimit` 且需要跨页一致排序，再重新评估索引侧排序。
